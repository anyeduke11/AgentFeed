# D2 消费信号回流设计稿（v0.2.x 蓝本）

> 来源：v0.1.5 PRD 3.3.4 D2（纯文档，零代码）+ 3.3.11 K1 三节增补（上下文编译器 / 信号管道双消费者 / 元飞轮，2026-09-21 裁决收编）。
> 性质：设计稿。实现属 v0.2.x，启动判据见第 7 节——本版不写一行回流代码。

## 1. 背景与问题：消费信号在采不回流

供给管线（采集 → 门禁 → 蒸馏 → wiki）已全链交付，消费侧埋点也已齐备（`mcp_call_logs` 三核心工具全落库、`read_history` 按 source 区分五渠道）。但两条信号目前只进诊断、不进决策：

- **漏斗断链**：E1 诊断实证 level1 链路完成率 0%（search 25 次，read_entry 跟随 0），25 条日志 24 条 args 为 NULL。检索返回了什么、agent 有没有深读，系统只记录、不学习。
- **排序不学习消费结果**：wiki 词条的排序先验是 `quality_score×3 + rule_score`（getContext/推荐池共用口径），全部来自供给侧（蒸馏质量 + 规则命中），一个从未被任何 agent 或人消费过的词条，与被反复深读的词条在排序上无法区分。

一句话：**采集侧已经知道「谁被消费了」，排序侧却当它不存在**。D2 要回答的就是这口气怎么回流、回流什么、怎么防反噬（Goodhart）。

## 2. 上下文编译器视角：记忆栈分层与可复现原则

把 AgentFeed 看作一台「上下文编译器」：原料是 agent 产物语料，产物是三层记忆栈，模型（LLM）只是编译器里的一个可替换 pass。

| 层 | 内容 | 时效 | 可变性 | 载体 |
|---|---|---|---|---|
| **L0 语料** | 扫描根内原始产物文件 | 永久 | 不可变（`files.md5` 在案，墓碑/复活由 md5 判定） | 磁盘 + files 表 |
| **L1 领域聚合** | 领域 top 词条要点、先验排序 | 实时 | 每次调用现算，无 DDL（`context.ts aggregateDomainContext`） | 内存（getContext 出口） |
| **L2 用户画像** | 角色断言 + 领域倾向 | 30 天窗口滚动 | 可否决可回滚（J1 版本链 `user_profile`，vetoed/user_added/预算三护栏） | user_profile 表 |

**编译产物可复现原则**：同一份 L0 + 同一套规则 + 同一个模型 ⇒ 应产出可逐字节对照的编译产物。这是「模型是耗材、脚手架是资产」的地基——模型换了，资产（语料、聚合逻辑、画像版本链）不动，只需重编译。

**B1 指纹是「重编译」的前提**：`exportWiki.ts` 对每个词条 entry.md 算 SHA-256，manifest 携带语料指纹（filesCount + maxFileId）。模型升级后的 recompile 之所以敢跑、跑完之所以敢信，是因为有指纹对照能回答「输入变了还是编译器变了」。

**recompile 三门激活口径**（PRD v2.4 再补行，2026-09-21 裁决：进 v0.2.x 候选池 + 三门激活，防烧钱在无人读的记忆）：

| 门 | 条件 | 提供的能力 |
|---|---|---|
| 门 1 | E1 归因完成 → 复用率基线数字出现 | 知道哪些词条被 agent 消费过（首跑白名单） |
| 门 2 | G1 落地 → 成本可见 | 知道重蒸馏要花多少钱（`ai.pricing` + 日预算闸） |
| 门 3 | B1 落地 → 指纹对照 | 重编译前后可机械 diff，漂移可检测（`baseline:check` 三态） |

三门齐后激活：**首跑仅重蒸馏 agent 消费过的词条（复用率加权），不做 4.85 万无差别全量**。

## 3. 信号管道双消费者架构：aggregate.ts 不另起炉灶

J1 已交付 `server/src/profile/aggregate.ts`：四路信号（`read_history` / `chat_messages` / `mcp_call_logs` / `exec_queue`）在模块内聚合成「统计数字 + 标签权重」的信号包（`ProfileSignalBundle`），隐私边界在聚合层收口——离开模块的只有统计包，无原始内容。D2 的排序回流直接挂在这条管道上做第二个消费者，不再建第二套聚合：

```
 信号四路                     共享聚合管道                    消费者
┌──────────────────┐   ┌────────────────────────┐   ┌─────────────────────────┐
│ read_history     │   │                        │──▶│ 消费者 A：画像蒸馏（J1）  │
│ mcp_call_logs    ├──▶│  aggregate.ts          │   │  bundle+上版 → LLM →    │
│ chat_messages    │   │  buildProfileSignal-   │   │  user_profile 版本链     │
│ exec_queue       │   │  Bundle()              │──▶│ 消费者 B：排序回流（D2） │
└──────────────────┘   │  · 30 天窗口           │   │  消费信号 → 排序先验权重 │
                       │  · 域归并/标签三态加权  │   │  （写先验，不动 L0）     │
                       │  · 出口=统计包（无原文） │   └─────────────────────────┘
                       └────────────────────────┘
```

- 消费者 A（画像蒸馏）已交付：统计包 + 上版画像 → LLM → schema 校验 → `user_profile` 版本链。
- 消费者 B（排序回流）是本稿第 4 节的设计对象：同一统计包派生词条级消费权重，注入排序先验。
- 共享管道的纪律：**回流计算全在本地聚合层完成，LLM 不参与回流数值计算**（AI 化判据见 `docs/model-switch-sop.md`——判断可 AI、执行必代码，排序权重是执行）。

## 4. 回流方案设计（v0.2.x 候选蓝本）

### 4.1 回流信号选型：read follow-through vs 打开率

| 维度 | read follow-through（search 后 30min 内 read_entry 跟随） | read_history 打开率（人读次数归并到词条） |
|---|---|---|
| 信号含义 | agent 觉得搜索结果值得深读——直接度量检索质量 | 词条被人类消费——度量内容价值 |
| 抗操纵 | 强：read_entry 参数是 file id，绕不开 search 返回 | 弱：打开可被列表位次导流（排序→打开→回流→排序，闭环自激） |
| 冷启动 | 依赖 search 量（当前基数小，单词条权重抖动大） | 依赖人读习惯（人读低频时信号稀疏） |
| Goodhart 风险 | 标题党化：标题吸睛→search 命中→read 跟随→权重升，正文质量无关 | 排序固化：热词条权重升→位次靠前→更易被打开，长尾永无出头 |

**倾向**（草案，待 v0.2.x 数据裁决）：以 follow-through 为主信号、打开率为辅信号。理由：本项目第一消费者是 agent（见 `knowledge-flywheel-design.md` thesis），follow-through 直接度量「检索结果对 agent 有用」；人读打开率与推荐池排序存在闭环自激，只作次级折扣项不作主项。

**冷启动防抖——权重公式草案**（明确标注：草案，数字未经数据校准，落地前需用 E1 基线重放验证）：

```
followBonus = Σ follow-through 次数 × decay(频次)
decay(频次) = 1 / (1 + ln(1 + 频次))          # 对数衰减：高频词条边际递减，防头部固化
prior = quality×3 + rule + followBonus         # 在既有双轨先验上叠加，不替换
```

- `quality×3 + rule` 是现状（getContext/推荐池口径），回流只做**加法项**——既有先验继续兜底冷词条，新词条无消费记录时权重退化为现状，零回归风险。
- 对数衰减同时防两头的 Goodhart：高频词条加不上太多（防排序固化），低频词条一次真实深读就有可感知增益（冷启动防抖）。
- 防标题党化不靠公式靠门禁：标题由蒸馏产出的 `cleanTitle` 截断刻度控制（80/160），回流权重只挂词条不挂标题字段，标题改写不继承消费权重。

### 4.2 triage pull 化：蒸什么由真实 query 驱动

现状 triage 是 push 式（按优先级队列顺序蒸）。D2 方向：用 `mcp_call_logs.args` 里沉淀的真实 query 驱动「蒸什么」——被 search 命中但尚无蒸馏产物的文件，优先入队。

- **前置依赖：存量 args NULL 清偿**。E1 实证 25 条存量日志 24 条 args 为 NULL（不可逆，如实标注「不可归因」单列）；新调用已 100% 落 args（200 字符摘要）。pull 化要等 args 覆盖率足够（新数据累积），否则「真实 query」本身就是残缺的。
- 与 A2 嵌入补嵌同思路：把算力从「无差别全量」转向「被消费意图指向的地方」。

### 4.3 隐私边界：回流计算全本地

- 回流权重计算只读本地表（`mcp_call_logs` / `read_history` / `wiki_entries_meta`），在 aggregate 层完成，**零外发、零 LLM 参与**。
- 中立性宪法（与 G3 评测同款自律）：回流不引入任何外部服务；权重公式可复现（同数据同权重），不依赖模型判断；任何回流数值可在看板审计（哪个词条、多少次跟随、当前权重）。

## 5. 元飞轮：AgentFeed 自举

本项目开发产物（DEV_LOG、PRD 演进、评审记录、本设计稿本身）已在扫描根内，被自身管线扫描、门禁、蒸馏——**AgentFeed 是自己最真实的测试语料**，且是唯一一条「生产者与消费者同体」的飞轮。

观察口径（如何度量「吃自己狗粮」的价值）：

- **主指标**：本项目相关词条（`source_agent` 归因到 AgentFeed 开发会话的词条，或挂 AgentFeed 领域的词条）的 **agent 消费率**——`mcp_call_logs` 中 search 命中本项目词条且 30min 内 read_entry 跟随的比例。开发中真实回查旧决策 = 飞轮在转。
- **辅指标**：本项目词条在 recompile 首跑白名单中的占比（复用率加权后值不值得重蒸馏自己）。
- 记录方式：沿用 E1 漏斗口径（`funnelCore.ts` 同源计算），按「词条是否属于本项目」分桶对比，不新建埋点。

## 6. 被否决备选

| 备选 | 否决理由 |
|---|---|
| **LLM-as-judge 逐次消费打分回流**：每次 read_entry/search 后调 LLM 给词条打分写回排序 | ① 二次 API 成本（每次消费多一次调用，随用量线性放大）；② 用模型评模型的循环依赖（judge 模型偏好会系统性偏置排序，且 judge 换代 = 排序静默漂移）；③ Goodhart 不可控（打分标准是模型隐式函数，无法审计无法复现，违反第 4.3 节中立性宪法）。与 G1 阶段否决「LLM-as-judge 幻觉率打分」同款裁决。 |
| 全量 recompile（换模型即重蒸馏 4.85 万词条） | 成本无门：三门激活裁决明确「防烧钱在无人读的记忆」，首跑仅 agent 消费过的词条。 |

## 7. 里程碑建议：v0.2.x 启动判据

**判据：复用率基线数字出现之后。** 具体为三门中门 1 先行——E1 主动验证走通（真实任务完整走 search→read_entry→get_source）且归因面板产出可持续观测的复用率基线（哪些词条被消费、比例多少）；门 2（G1 成本视图）、门 3（B1 指纹对照）v0.1.5 已交付，随基线数字自然补齐。

| 时点 | 条件 | 动作 |
|---|---|---|
| 现在 | 复用率基线未出（args 覆盖率在累积） | 只观测不回流：跑 E1 漏斗面板，累积 args 完整的新调用 |
| 基线出现 | 归因面板有 ≥2 周稳定数据，能回答「哪些词条被 agent 消费过」 | v0.2.x 启动 D2 实现：follow-through 权重草案用基线重放校准数字，再进代码 |
| D2 落地后 | 回流权重生效 | recompile 首跑（白名单 = agent 消费过的词条），元飞轮指标开始记录 |

任何时点若发现回流导致排序头部固化（长尾词条曝光单调下降），触发 Goodhart 复审——回退为先验加法项关闭（`prior = quality×3 + rule` 现状），回流只观测不生效。
