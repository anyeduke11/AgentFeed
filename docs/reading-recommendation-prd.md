# PRD：人读推荐专区与阅读执行闭环

> 版本：v2.1（2026-09-15）· 状态：M3 实现前规格补充（新增 7.1 rule_score 维度定义）；上版 Phase 2 更新（M3 细化 + 人读场景包 R1~R4），三维审查通过（P0 已回写）
> 范围：AgentFeed 发车区「人工阅读」Tab · 总览执行区块 · 阅读回顾闭环
> 上游状态：M1/M2 已交付（推荐池、打分闭环、AI 策展、间隔重复）；截至 v2.0 时的真实数据：推荐池 10 篇全部 curated/unread，本周打开 0 次、打分 0 次，蒸馏队列仍有约 3 万积压

## 第 1 章 · 产品概述与目标

**定位**：把看板从「给 agent 用的知识库」升级为「人机共用的学习系统」——机读走 MCP，人读走推荐，读完转执行，执行后回顾巩固。

**闭环（7 站，与站牌编号一致）**：

```
01 总览 · 02 收件坪(入库) · 03 精炼线 · 04 成品仓 · 05 分拣区
→ 06 发车区（机读 MCP ＋ 人读推荐）→ 执行（总览执行区块）→ 回顾（周期巩固）
```

**核心目标**（v2.0 重排：从「功能齐备」转向「真实用起来」）：
1. 闭环真实发生：周打开 ≥ 5 篇、打分率 ≥ 60%（当前为 0，先建立每日入口与进度回溯两个习惯锚点）
2. 冷启动可用：推荐池为空时，四维筛选+搜索即时生成可读清单，收纳零摩擦（已达成，保持）
3. 越用越准：read_history（打开/星值/可执行性/进度）反哺推荐排序；推荐质量有客观分兜底

**成功指标**：推荐池收纳 ≥ 20 篇且已读率 ≥ 50%；稍后试文章 7 天内重读率 ≥ 40%；周回顾自动生成且含待执行清单；每日精选点击率 ≥ 1 次/日。

## 第 2 章 · 用户画像与场景

单用户（本机用户），macOS 本地系统，安全行业从业者。核心场景（用户故事）：

- 作为用户，推荐池还是空的，我希望按「人工智能领域 + RAG 关键词」立即看到一批好文章，以便马上开始阅读（冷启动预览，M1✓）
- 作为用户，我读完一篇教程觉得能上手，我希望标记「稍后试」，以便它别沉底、到点提醒我实操（执行召回，M1✓）
- 作为用户，我希望 AI 给的推荐带理由，以便判断值不值得点开（理由展示，M2✓）
- 作为用户，长文一次读不完，我希望标记「读到 50%」，下次打开时提示上次进度，以便不从头找位置（**R1 阅读进度**，新增）
- 作为用户，我每天打开看板不想纠结「读哪篇」，希望有固定的「今日 3 篇」，以便零决策进入阅读（**R2 每日精选**，新增）
- 作为用户，我希望每周有一个阅读目标（如 5 篇），回顾卡告诉我完成度，以便保持节奏（**R3 目标环**，新增）
- 作为用户，我希望每周自动回顾读过什么、哪些待执行、掌握薄弱在哪，以便巩固学习（回顾，M2 基础版✓ → M3 深化）

使用频率：阅读 5~10 篇/周；回顾每周一次（自动生成）。

## 第 4 章 · 系统架构设计

技术栈不变：Vue3 + Pinia（前端）/ Express + SQLite（后端）/ LLM 队列复用（job type：distill/assess/curate + **backfill**）。

```
web/src/views/Supply.vue        B3 进度条 + 快捷档（R1）
web/src/views/Overview.vue      每日精选卡片（R2）+ 目标环（R3）+ 薄弱点（M3）
web/src/components/AppModal.vue rate 弹层联动进度预填（R1）
web/src/api.ts                  api.reading.progress / api.recommend.daily
server/src/routes/recommend.ts  GET /daily（无状态轮转）
server/src/routes/reading.ts    POST /progress；GET /stats 扩展薄弱点聚合
server/src/llm/llmWorker.ts     job type 扩展：backfill（质量分补齐，priority=0 不插队）
server/src/db.ts                recommendations 扩列 progress/last_progress_at；config 键
```

**LLM 成本**：理由升级 ~200 token/篇；策展 ~4k token/次；**质量分补齐 ≤200 篇 × ~200 token ≈ 4 万 token（一次性，封顶）**。全部走现有队列并发与暂停机制；补齐与蒸馏共用 priority=0，避免挤占 assess/curate。

**外部约束**：原文经系统打开后在外部应用（浏览器/编辑器）渲染，站内无法感知滚动与停留 → R1 的所有进度语义均为用户手动声明，系统只做存储、展示与调起提示。

## 第 5 章 · 业务流分析

**主流程（阅读闭环，M1/M2 已跑通）**：

```
用户进入发车区人读 Tab
  ├─ 推荐池有货 → B1 精选 / B3 列表 → 点开原文（埋点 read_history）
  └─ 池空/不满意 → B2 冷启动预览 → 即时列表 → 打开或收纳
阅读完成 → 打分弹层（星值 + 立即试/稍后试/纯了解）
  ├─ 纯了解 → status='read' 归档
  └─ 立即试/稍后试 → 入执行队列（due_at：立即试=当天，稍后试=1 天后）
执行区块：到期置顶 → 重读/实操 → 标「已执行」出队 → 星值驱动间隔重排
回顾（每周）：汇总阅读/打分/执行 → 权重反哺排序 → 薄弱点提示
```

**R1 进度流（新增）**：

```
B3 行内（或打开时 toast）点快捷档 → POST /reading/progress
  → recommendations.progress 更新 + last_progress_at 刷新
下次打开池内文件 → 后端返回 last progress → toast「上次读到 50%」
读毕 → 打分弹层显示当前进度；进度 100% 时默认聚焦星值（顺手完成闭环）
长文暂停 → 标 50%/75% → B3 该行显示进度条 + 「在读中」，状态仍算 unread
```

**R2 每日精选流（新增，无状态轮转）**：

```
GET /recommend/daily
  池内 unread 按 score 降序排列 → 按 epochDay % ceil(n/3) 取窗口滑动
  → 确定性选出今日 3 篇（同一天多次请求结果一致，次日自动轮到下一窗）
  池内不足 3 篇 → 预览高分（未入池）补位，卡片标「池外推荐」
总览执行区块旁展示 → 点开即埋点（source=daily）
```

**异常流**：
- 外部卷未挂载时打开外部词条 → 提示降级，仍记录打开意图
- LLM 队列暂停时收纳文章 → 规则理由照常，理由升级挂起，恢复后补跑
- 打分弹层关闭（未打分）→ opened 记录保留，不强制
- 进度长期未更新（>14 天且 <100%）→ 周卡「在读停滞」提示（不自动改状态）
- 补齐任务对无有效内容的文件 → 记 failed 跳过，不重试堵队列

**模块联动**：蒸馏完成（quality_score 落地）→ 自动入池判定（≥70，M3 后分数更可信）；执行完成 → 回顾统计；回顾 → 权重（打开 ×1.2、5 星 ×1.5、已执行 ×1.5）+ 薄弱领域提升采样权重（M3，仅影响预览排序 tie-break，不做硬干预）。

## 第 6 章 · 操作流分析

**日常**：打开看板 → 总览「每日精选」扫一眼（R2）→ 执行区块看今日到期 → 发车区人读 Tab 阅读/续读（R1 toast 回溯）→ 读完打分（10s）。

**周期**：AI 策展为**手动触发**（v1.0 写的「每周日 20:00 自动」未实现且用户未提出强需求，按现状回写；若后续形成周节奏可在 M5 加懒生成）；每周一回顾卡懒生成。

**自动化**：read_history 埋点（零操作）；理由升级（队列插队）；due_at 到期计算（查询时算，无定时器）；质量分补齐（手动触发一次 + 进度可查）；进度提醒（打开时计算，无定时器）。

**记忆规则（间隔重复，简化 SM-2，M2 已实现）**：done 后按最新星值排下一轮——5 星：1→3→7→14→30 天；3~4 星：1→3→7 封顶；≤2 星：归档不再调起。「到期忽略 >7 天」降一档并附回顾提示。**多轮复习通过 exec_queue 多行实现（v2.0 已去 file_id UNIQUE）**。

实体关系：files 1—N read_history / reading_feedback / exec_queue；recommendations 1—1 files。排序权重视图 = quality_score（wiki_entries_meta）+ rule_score + 行为加权（打开/星值/执行）+ R1 进度仅展示不参与排序。

### 7.1 rule_score 维度定义（M3 rule_score 完整化规格）

**总则**：纯规则计算，零 LLM 成本；总分归一化为 **0~10 分（1 位小数）**，缓存于 `files.rule_score`（REAL 单列，不存维度明细，明细可由内容重算）。内容只采样**头部 512KB**（与门禁共用 `SIZE_ANALYZE_LIMIT`），超大文件不整读（防 OOM）。`raw = D1+D2+D3+D4+D5`，`rule_score = round(raw / 14 × 10, 1)`。

| 维度 | 上限 | 提取方式 | 计分 |
|---|---|---|---|
| D1 文件类型（现有） | 2 | 扩展名 | .html = 2（自带排版与链接结构），.md = 1 |
| D2 内容规模（现有） | 3 | 文件字节数 | >50KB = 3；>10KB = 2；>2KB = 1；否则 0 |
| D3 标题层级结构 | 3 | md：`^#{1,6}\s` 行计数；html：h1~h6 标签计数。层级数 = 出现的不同标题级别数 | 0 = 无标题；1 = 有标题但层级单一或总数 <3；2 = ≥2 级且总数 3~5；3 = ≥2 级且总数 ≥6 |
| D4 表格行数 | 3 | md：以 `\|---\|` 分隔行定位表格，累计各表数据行；html：`<table>` 内 `<tr>` 计数 | 0 = 无表格；1 = 仅 1 表且 <5 行；2 = ≥2 表或 5~19 行；3 = ≥20 行 |
| D5 代码围栏占比 | 3 | md：``` 围栏对内行数；html：`<pre><code>` 内行数；占比 = 代码行 / 非空总行 | 0 = 无代码；1 = ≤10%；2 = 10%~30%；3 = >30% |

**护栏（防刷分与误判）**：
- 非空行数 <5 的样本（压缩单行 html、代码片段文件）不计占比类指标，D5 按 0 分
- 代码占比 >80% 且 D3 = 0（纯代码堆砌、无讲解文字）→ D5 封顶 2 分
- 内容读取失败（文件已删除/外部卷未挂载）→ 跳过不写值，不阻塞扫描

**计算时机**：
1. **扫描/入库**：`ingestFile` 内，md5 变化或 rule_score 为 NULL 时精算并写库（内容改动即刷新，与门禁读取复用同一次内容缓冲）
2. **存量回填**：服务启动后台分批回填（每批 200 条，纯 CPU 零 token），一次性追平；未回填的 NULL 行在排序中按 0 兜底（次级排序 size DESC 仍生效）
3. M1 的 SQL 估分（`backfillRuleScore`：ext + size 直更）**删除**，计算源统一为 TS 精算，避免同一列出现两套刻度

**兼容性**：rule_score 仅参与排序相对比较与入池 score 合成（`quality_score×3 + rule_score`），无绝对阈值依赖；刻度从 1~5 改为 0~10 只影响未蒸馏层内部的相对排序（预览分层规则「有质量分层优先」不变），无回归风险。池内已有 `recommendations.score` 为历史合成值，不追溯重算。

## 第 8 章 · 开发优先级与里程碑

## 第 9 章 · 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
