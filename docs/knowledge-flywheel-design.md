# 知识复利方向设计（需求重梳理 v1）

> 来源：office-hours 诊断会话（2026-09-19），方向=开源+创业，startup 模式。
> 性质：设计文档，不含实现代码。

## 1. 诊断结论（为什么重梳理）

证据表（声明 vs 证据）：

| 维度 | 声明 | 证据 |
|---|---|---|
| 人读需求 | 高频刚需 | ❌ `read_history` 全历史仅 3 次（09-15/16），之后为零 |
| 机读需求 | 在用 | ❓ MCP 无调用日志，不可证伪 |
| 现状替代 | 手动归档笔记 | ✅ 与产品主张自洽 |
| 具体用户 | 我自己 | ✅ 诚实，pre-product |

失败模式命名：**「为那个不存在的用户持续加功能」**——9 个 view、M1~M5 全交付、3 万蒸馏积压，对面没有一个被验证的消费者。

竞品 landscape（品类词搜索）：mcp-local-rag / LocalSynapse / Lorekeeper / LobeHub 本地知识库——全部是「手动喂文件做检索」。无人做「agent 产物持续自动捕获 + 质量门禁」。差异位存在，但需求未验证。

## 2. 产品 Thesis v1：知识复利 + Agent 数据联动

- **表面层**：历史 agent 产物 → 门禁 → 蒸馏 → wiki → 给其他 agent 消费（MCP 出口）
- **核心层**：用户的知识/技能/能力通过 agent 持续复利；多 agent 联动是趋势
- **消费者重定义**：第一消费者是 agent，不是人；人的收益通过 agent 间接实现

Thesis 的承重前提：**旧知识被新任务消费（复投）**。人读侧复投 = 0；机读侧复投 = 无数据。整个 thesis 压在机读侧，因此埋点是第一优先级。

## 3. 前提清单与验证顺序

| # | 前提 | 状态 | 验证方式 |
|---|---|---|---|
| P1 | 痛点真实（产物想不起来、回不去） | 部分证伪（人读 3 次） | 随 V1 复投数据再看 |
| P2 | 系统形态必要 | 论点存活（复利+联动 > 纯检索器），但依赖 P4 | 机读调用数据 |

| P4 | 机读消费真实发生 | **不可证伪，第一优先** | mcp_call_log 埋点，观察 2 周 |

## 4. 阶段路线（每阶段设裁决条件，不达标即停）

### V0 验证埋点（约 1 天）
- MCP server 端新增 `mcp_call_log` 表（tool / args 摘要 / ts），7 个工具全覆盖
- 蒸馏策略预留从 push 转 pull：按调用数据决定「蒸什么」，不再批量清积压
- **裁决**：2 周内 ≥20 次真实工具调用且跨 ≥3 天 → 进 V1；接近 0 → thesis 降级，回薄工具或放弃

### V1 复利最小闭环（自用验证）
- wiki 质量化：存量精选而非批量 3 万；按 domain 树挑 top 领域先做
- MCP 暴露 wiki 检索工具，供 Claude Code 等 agent 在任务中消费
- 成功标准：agent 在真实任务里引用 wiki 内容（抽查会话可证）

### V2 Agent 数据联动
- 跨项目/跨 agent 归因图谱（复用 scanner 归因信任序）
- 产物间关联（引用/领域/时间线）
- 开源发布试水：抽包或整仓发布 + 一条 HN/V2EX 帖，验证 P3

### V3 联邦与规模化
- V2 达标后才启动，本文档不展开
