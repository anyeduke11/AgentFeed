## Problem Statement

AgentFeed 的两类消费者都停在「能查」而非「好用」：

- **Agent 侧**：MCP 7 工具已挂载，工具级调用日志已有（`mcp_call_logs` 表 + `/api/stats/mcp`），但**缺 args 级记录**——查了什么、返回有没有被用，未知；没有开场注入能力；agent 查到的多是原文，缺可直接吃的摘要。
- **人侧**：看板 8 个 view 质量不差，但全历史只打开 3 次——「等人来」已被证伪。

本次会话把双方消费时刻全部落定（用户逐条确认）：
- Agent 时刻：**任务中主动查询（B，地基）→ 任务开场注入（A）→ 跨 agent 交付（C）**，依赖递进。
- 人时刻：**推送日报（A）+ 会话内问答（B）**，两条都不依赖看板。

## What Makes This Cool

「你不访问 AgentFeed，AgentFeed 来找你」。四个出口，编号全文沿用：**出口 1** MCP 查询（agent 任务中主动查，地基）；**出口 2** getContext 开场注入（agent 开工自动带历史上下文）；**出口 3** 日报推送（人每天收到「我的 agent 们今天干了什么」）；**出口 4** 会话内问答（人直接问自己的 agent 查全部历史）。看板退居运维后台。同一条蒸馏管线，喂四个出口。

## Constraints

- 在现有基础上改：scan / gate / distill / MCP / web 全部复用，不重写
- 红线（CLAUDE.md）：扫描根边界、阅读器零脚本、`ensureColumns` 幂等迁移、`{ success }` 响应、埋点 source 集合
- 看板冻结：只维护，不加新 view

## Premises

1. **出口 1（MCP 查询质量）是地基**——注入/日报/问答全吃它的产出；查不到好东西，三个上游全是垃圾进出
2. **看板冻结**——人侧消费走日报+问答，不走看板
3. **3 万积压不批量清**——按领域 triage，top 领域精选 ~500 篇，蒸多少由出口需求拉动

## Approaches Considered

- **A 最小可行（查得好+日报）**：补 args 埋点 + 精选蒸馏 + 日报落盘 → 用户采纳为第一期
- **B 理想架构（一个管线四个出口）**：A + getContext 注入工具 + 问答优化 → 采纳为第二期
- **C 反向写回（agent 集体记忆）**：agent 会话结束写回学到的东西 → 采纳为第三期实验，带淘汰条件
- **D 埋点后再定**：用户否决——不再空等两周数据，要看得见的改进；现有工具级日志已够判断「用没用」，只补 args 摘要列作为第一期的一小步

## Recommended Approach

用户选择 A+B+C 全要。不平均、不并行——翻译为**三期串联**，每期有验收与裁决：

### 第一期（A）地基：查得好 + 日报

1. **盘点而非新建**：`mcp_call_logs` 表与 7 工具埋点已存在（db.ts / mcp.ts），缺口仅 args 摘要列——`ensureColumns` 幂等加列（截断 JSON，~200 字符），不建新表
2. 蒸馏 triage：按领域树选 top 领域，精选 ~500 篇蒸馏（pull 模式，不清积压）。高质量判据 = 蒸馏成功且摘要非空且命中 top 领域；预算上限 = 按篇 × 单篇预估 token 计，超限即停；服务商沿用现有配置；重试沿用 llm 队列既有机制，连续失败熔断（机制不足则单列小任务）
3. 日报生成器：每日新增蒸馏产物 → markdown + HTML 日报（今日产出 / 值得看 3 篇，复用 `/api/recommend/daily` 轮转逻辑）；落盘目录避开已启用扫描根（防扫描器二次采集），因此新增**专用日报端点**打开 HTML（目录白名单 = 日报落盘目录，直写 `read_history` source=`daily`，file_id 置空）。此为扫描根红线的一处**显式豁免**，理由：目录为系统自产、路径固定，非用户语料

**验收**：2 周内 ≥20 次真实 MCP 调用且跨 ≥3 天（现有日志即可统计）；日报连续产出 7 天且 HTML 打开 ≥5 次。
**失败裁决**：调用未达标 → 第二期降级为工具打磨（不扩张出口），仅保留日报；日报打开为 0 → 重议投递渠道（落盘→推送），不直接砍。

### 第二期（B）四个出口全通

4. `getContext(domain)` MCP 工具：返回领域摘要 + top 产物清单（供开场注入）。摘要生产者 = 蒸馏管线按领域聚合（蒸馏完成时增量更新）；top 产物按 score / mtime 排序取前 N；token 预算见 Open Questions
5. 各项目 CLAUDE.md 加一行开工指引（先调 getContext）——逐项目手动加，这是推广成本所在
6. 问答出口落地：`search_knowledge` 加时间窗参数（since/until）或新增 `recent_activity(since)` 工具，实现时二选一——支撑 agent 回答「这周我的 agent 都干了啥」；工具描述优化仅作配套

**验收**：≥2 个项目实际用了注入；时间窗问答抽查 3 次回答可用。

### 第三期（C）反向写回（实验，带淘汰条件）

7. `recordSession` MCP 工具：agent 会话结束写回结构化学到的东西（领域/要点/产物链接）——落**独立实验表**（如 `session_notes`），不进 scan/gate 主链路，不污染语料
8. 日报升级为「agent 集体日记」（数据源含 session_notes）

**淘汰条件**：第一期埋点显示查询频次 <5 次/周 → C 永久搁置。没有读方，写回无意义。

## Open Questions

- 日报投递渠道：先落盘，微信/邮件推送后置，渠道未定
- `getContext` 注入摘要的 token 预算（多少合适）

## Success Criteria

合并进各期验收（见上）。总纲（全部可度量）：出口 1 = `mcp_call_logs` ≥20 次真实调用跨 ≥3 天；出口 3 = `read_history`（source=daily）≥5 次；出口 2/4 以各期验收为准。

## Distribution Plan

本地服务沿用 `service.sh` 部署。开源发布延后至第一期数据达标后，沿用 flywheel 文档策略：npm 包或整仓发布 + HN/V2EX 单帖试水。

## Next Steps

1. 盘点 `mcp_call_logs` 现状，`ensureColumns` 补 args 摘要列（唯一先动代码的基建，半小时级）
2. top 领域选定 + triage 蒸馏跑批（带预算上限）
3. 日报生成器 v0（markdown + HTML，专用端点打开并记 source=daily）

## The Assignment

今晚把 AgentFeed 的 MCP server 挂进你日常用的 Claude Code 配置；明天第一个真实任务里，手动让 agent 调一次查询工具（search 或 list 皆可），记下它查了什么、返回的东西有没有用。这是调用日志之外的第一手体感证据，也是明天日报的第一批素材。

## What I noticed about how you think

- 你说「表面上是找到历史 Agent 产物整合成 wiki 给其他 agent 消费，核心真实是用户通过 agent 不断的强化自己的技能，知识，能力」——你把产品定义为能力复利机器，不是文件检索器。
- 两次选「全部都要」（D1 的 ABC、D3 的 A+B+C）——你不砍愿景，但接受排序。所以本文档把「全要」翻译成带淘汰条件的三期，而不是三选一。
- 你对「先埋点等两周」说不——上次会话的作业你搁置了，你要的是看得见的改进。这期把埋点压缩成第一期的一小步，埋点服务于改进而不是替代改进。
